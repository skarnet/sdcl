SDCL design document

Fundamental goals

The SDCL language is meant to:

  • Be written, read and understood by humans, not automation. It must be friendly for humans to read, write and edit. This means:
    • Its syntax must be clear and concise, and must not have gratuitous annoyances.
    • Its semantics must be intuitive and represent the human understanding of a service
    • If the sdcl tool has to be more complex in order to parse the syntax or to transform the human view of a service into something that is actionable by a service manager, so be it — that's exactly what it's for.
  • Modelize, in a generic way, a set of services running on a system, under a service manager. The following invariants must be true:
    • A service definition can be provided without knowing the details of of the service manager that runs it, or the system it is running on.
    • The administrators can input information about their system (the policy file) without modifying the service definitions.
    • The sdcl tool takes a policy file and a set of service definitions, and outputs a set of files and directories that is suitable for the chosen service manager.

Specifications

  • The specification for the SDCL language is described here. For now, it is just a draft. The grammar will be formalized last, because we want the freedom to modify it as we iterate on the spec and find what is most comfortable.

Internal representation

The original plan was to have the sdcl command, aka the frontend, read a set of files written in the SDCL language and process them into an internal representation that would then be serialized and given as input to the backends, i.e. the programs that output service files for various service managers.

After thinking long about it, this does not feel like the optimal design.

  • Most of the transformations are performed by the backends.
  • Having the frontend parse a set of SDCL files, process it into an internal representation, and serialize it to text format, only for the backends to process that text format and perform their own transformations and outputs seems wasteful:
    • It requires designing two text formats rather than one.
    • It turns the frontend into a preprocessor with little added value, since not many transformations are performed. Even if the frontend does e.g. dependency checking between services, since the backends read text input that has to be untrusted, they have to perform the dependency checking again.
    • It requires every backend to process text into its own internal representation, incurring more burden for backend writers.

Consequently, there will not be a serialized internal representation format for SDCL. Instead, the frontend will be a library, that the backends will use to parse SDCL files directly into their memory, which will make it easier for them to access service data in a convenient representation and transform it.

The library functions will be documented here.

Various language bindings can be added later, so backends can be written in other languages than C.
