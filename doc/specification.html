The SDCL specification

Versioning

For simplicity purposes, the version number of the SDCL specification is tied to the major number of the sdcl package (which means, the first two numbers of the 4-number version). So, this specification defines version 0.0 of the SDCL format.

Basic definitions

  • SDCL, in capital letters, is the name of the language the service definitions are written in.
  • sdcl, in lowercase, is the name of the tool that reads SDCL and outputs a set of files directly usable by a service manager.
  • An SDCL file is a text file containing a series of sections, which are the primary entity in the language.
    • The sdcl tool can be given one or several files to read, or an input stream; it does not use file boundaries as logical boundaries. The only boundaries it uses are sections.
    • Of course, file boundaries are beneficial for users and for package managers, so it is recommended to use one file per service; every service definition section goes into its own file.

Syntax

Line format

  • A quoted string begins with an unescaped " (doublequote) and ends with an unescaped ".
  • Characters can be escaped inside a quoted string by prepending them with a \ (backslash). Their meaning may then change.
  • Some characters have a special meaning in a quoted string, and lose it when escaped:
    • \ (backslash) escapes the following character.
    • " (doublequote) ends the quoted string.
    • $ (dollar) starts a variable substitution.
    • An escaped newline is entirely ignored. This makes it possible for users to split long lines.
  • Some characters have no special meaning in a quoted string, but gain one when escaped:
    • Escaped n means literal newline.
    • Escaped t means literal tab.
  • A line is the sequence of characters between two unescaped newline characters. The first line of a file is the sequence of characters up until the first unescaped newline.
  • Whitespace is defined as spaces, tabs and carriage returns.
  • If a line starts with a # (sharp) character, or any amount of line whitespace then a # character, it is considered a comment, and entirely ignored. The next newline character ends the comment, even if it is preceded by a backslash or anything else.
  • Inside a line, words are sequences of non-whitespace characters, separated by any amount of whitespace.
  • A quoted string is always treated as one single word, even if it embeds whitespace. This is the main point of quoting.
  • Some semantic elements, such as directive definitions, will be considered separate words even if they're not separated by whitespace. This is on a case by case basis and dependent on the semantic element, see below.
  • Example: start="foo bar" qux → divides into three words, start=, foo bar, and qux, because the start= directive definition always ends at the = (equals) sign.

Semantic elements

Section

  • A section is said to be global if it appears at the top level, and local if it appears inside of another section.
  • A section is made of the following:
    • The section type:
      • policy
      • default_service
      • variables
      • service
      • dependencies (local-only, inside a service)
      • logging (local-only, inside default_service or a service
    • An optional section name, for service sections only.
    • A { (opening curly brace) character
    • Zero or more directive definitions or nestable sections
    • A } (closing curly brace) character.
  • Every global section is unique except service.
Policy

The policy section defines the operating system's policies: how it invokes the service manager, where the service files are stored, etc. It is meant to be written and maintained by distribution packagers and should reside in a place that is not accessible by individual services; we advise creating a policy file just to hold the policy section.

sdcl expects the policy section to be the first section it reads. That is why it has options to specify the policy file: it will read and process the contents of that file first, no matter what other arguments it is given.

Default service

The default_service section looks like a regular service, but provides defaults that will be inherited by all the services. It can include a logging subsection (or several, but this is rare) and even a dependencies one, although it is not recommended to have many dependencies by default.

Variables

The variables section defines variables that can be reused in the context where this section is defined.

  • There can be a unique global variables section.
  • A local variables section will define variables that will only apply to the section it is local to.
  • Yes, it is possible to nest a variables section with itself. It is, however, probably not a good idea.
Service

The service sections are the bread and butter of SDCL. This is where services are defined. These sections are meant to be written by package maintainers and provided in distribution packages, independently from any policy. When installing a package, the package manager can invoke sdcl on the SDCL file containing a service section; sdcl pairs it with the local policy file and can instantly output the service files for the local service manager.

A service section can embed a local variables section, but it is not mandatory. Same with a local dependencies section.

Logging

A logging section can only appear in a default_service or service section. It is local to a service, and unique to it. As the name implies, it describes the parameters of a logger for this service. Several loggers (in order to log separate streams) can be defined by having several logging sections for the same service. This can be useful for services such as certain web servers that have separate access and error logs; but most services will only have one logger.

Dependencies

A dependencies section can only appear in a default_service or service section. It is local to a service, and unique to it. As the name implies, it holds dependency information for the service.

Directive

Where sections are the structure of an SDCL file, directives are its contents. A directive is the fundamental declarative element of SDCL, assigning a value to a property.

  • Directives appear in every section.
  • There is always one directive per line. (Per logical line. Escaping newline characters is the way to write a directive over multiple physical lines.)
  • Most directives take the form of a simple assignment: key=value. But this is not always the case: in dependencies sections, directives use a different syntax.
    • Whitespace is permitted in directives: key = value is the same as key=value. The start of value is the first non-whitespace character. value can start with whitespace if it is quoted: key=" something".

List of available directives

Directives for the variables section

The variables section is a list of variable assignments. Every directive in this section is an assignment of the form var=value. Later directives in the variables section itself and the scope right outside of it can evaluate a variable with $var or ${var}.

Example: 

service foobar {
  variables {
    rootdir=/opt/foobar
    bindir=/bin
    rootbindir=${rootdir}${bindir}
  }
  start=${rootbindir}/foobar
}

Directives for the policy section

They all take the key = value form. The valid keys are:

version
The version of SDCL that the files are written in. The number is not expected to change often.
basedir
The place in the filesystem where the scripts and data produced by sdcl are stored.

Directives for the service section

type
The type of service: longrun for a long-lived process (daemon), oneshot for a short-lived process (that changes the machine state persistently), TODO: maybe others? longrun is the default, it is not expected from many packages to ship oneshots.
start
The command line that starts the service.
stop
For a oneshot: the command line that stops the service. For a longrun: either signal sig or command stopcommand, which should kill the process. If unspecified, which should be the case for a majority of services, the default is signal SIGTERM.
notify
The notification mechanism: either fd notif for the s6 notification protocol, or socket for the systemd notification protocol.
directory
The directory to chdir to before starting the service.
chroot
The directory to chroot to before starting the service.
umask
The umask used for the service's process hierarchy.
user
A user name to change uids to before running the service.
group
A group name to change gids to before running the service.
readiness_timeout
A timeout (in milliseconds) after which a service that isn't ready yet is considered failed.
death_timeout
A timeout (in milliseconds) that starts when the stop signal is sent (or the stop command is run). If the service still isn't down after the specified duration, a SIGKILL is sent to the process (for a longrun) or the transition is considered failed (for a oneshot).
cleanup
A command to run every time the service dies, even if it is restarted.
start_pre
A command to run once before start.
start_post
A command to run once after the service is ready.
stop_pre
A command to run once before the service is brought down.
stop_post
A command to run once after the service is brought down.

Directives for the logging section

The data stream that is logged. The value is a comma-separated list of file descriptors; stdout is an alias for 1 and stderr is an alias for 2. The output from the listed file descriptors will all be handled by the same logger.

Directives for the dependencies section

dependencies directives have a slightly different syntax. They are of the form: name : deptype, with mandatory whitespace around the colon, where name is the name of the service being declared as a dependency, and deptype is the type of dependency being set up. deptype is one of:

needed
The "hard" form of a dependency: if A is needed for B, then B will only be started when A is up and ready, and B will be stopped before A is stopped.

Yet-unspecified features

These are features that are not specified in this draft yet because they require more study to be adequately or satisfyingly represented.

  • Instanced service support. Instances are generally a vague, badly defined term: it can mean subtly different things in different service managers, and existing support is sparse at best.
  • Linux-specific features such as cgroups and namespaces. It would be good to be able to standardize some kinds of service isolation, but it would be even better to do that in an OS-agnostic way, without following the Linux terminology or isolation architecture, in order to preserve maximal sdcl portability.

Example

Here is an example of an aggregated SDCL file, what the sdcl tool could see as its input. In reality, these sections would probably be split into several SDCL files, but we're showing them all at once. 

policy {
  version = 0.0
  basedir = /etc/sdcl
}

default_service {
  stop = signal SIGTERM
  notify = fd 3

  logging {
    stream = stdout, stderr
  }
}

service foobar {
  name="foobar"  # redundant, optional, needs to match the service name if given
  start="foobard --notification-fd=3 --foreground"
  user="foobar"
  directory="/var/run/foobar"

  dependencies {
    network : needed
    bazqux : needed
    corge : optional
    grault : optional
  }
}

Grammar

Since the implementation can (and will) inform the specification, the grammar of the SDCL language will be formalized when the first implementation of the SDCL parser is complete. The list of supported directives will also be completed as the implementation advances; it is likely that this document will remain a skeleton and the full directive list will appear in another part of the documentation (such as a man page).
